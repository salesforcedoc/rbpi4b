# 12 — Troubleshooting

Symptom → cause → fix. Rows are grouped by subsystem; the ones marked
**(previous target)** are kept because they explain a design decision in this
port, even though the hardware that produced them is gone.

**Start here.** Before working down any table, run the unit's own check:

```sh
sh /opt/rblive4/doctor.sh
```

It changes nothing — no write, no mount, no module load, no `systemctl` call; the
one thing it executes is a chroot'd `busybox echo` — and it reports what it found
plus a single paste-ready fix block. Its most valuable row is the one this port
has most often got wrong: **each shim's deployed build against the copy `rbp` is
actually loading**, read out of the running process's `/proc/<pid>/maps`. That
answers "my new build made no difference" before you start debugging the build
itself ([17](17-rx3-flx4-comparison.md), where the idea came from). Every path it
tests comes from `rb.conf` and `lib.sh`, so it cannot drift from the scripts it
is checking.

## Nothing works at all

| Symptom | Cause | Fix |
|---|---|---|
| **The unit looks dead — nothing responds, not even the touchscreen** | this is an **audio** fault, not a display or an input one, and it presents as a total failure. The master's device is one that *opens* and then refuses every write, so rbp's recovery spins `prepare → write(-22)` tens of thousands of times a second until little else gets to run. Measured 2026-09-27 with no FLX4 attached: 13M failed writes, thread `JuceALSA` at ~43% of a core, `/tmp/audioshim.log` growing ~1 MB/s — **449 MB in eight minutes**, and `/tmp` is tmpfs, so that is RAM and it fills in ~25 minutes. Touch and keyboard *are* being read; the UI simply never paints | look at the audio master **before** the display or the input path: `grep -c "written=-22" /tmp/audioshim.log` and `wc -c /tmp/audioshim.log`. Both are now prevented — `default` is out of the device chain and a handle that never carries a frame is retired — so the log reads `MASTER LOST: the handle opened but never carried a frame` **once** and the paced no-device path takes over. The row below stages it deliberately ([09](09-audio.md)) |
| `fix-dev.sh` reports it cannot bind /device nodes are missing | not run as root, or `/dev` was rebuilt by a reboot | run `install.sh`/`start-rb.sh` as root; `fix-dev.sh` must run **after every reboot** ([05](05-chroot.md)) |
| rbp exits ~1 s after start, `crash.log` shows `[NULL+0x9c]` | `getPcController()` NULL deref | apply `scripts/patch-rbp-nopc.py` ([03](03-port-plan.md)) |
| `chroot … /bin/sh -c 'echo ok'` fails | the kernel cannot execute 32-bit ARM ELF (no `32-bit EL0`/`CONFIG_COMPAT`), or the chroot's exec bits are missing | `dmesg \| grep '32-bit EL0'` — `uname -m` is **not** the test, a 64-bit kernel is fine; reinstall Pi OS Lite 32-bit and rebuild the tarball ([05](05-chroot.md)) |
| `sh: ls: not found` in `rbp.log` | chroot launched without `/bin` in `PATH` | `PATH=/bin:/sbin:/usr/bin:/usr/sbin` — the launcher sets it ([11](11-runtime-launcher.md)) |
| **An SSH login has no prompt, no echo, no tab completion and no history** — the shell looks like it is not a shell | there is no pty, so `bash` runs non-interactive and prints nothing. `sshd` needs `/dev/ptmx` **and** the devpts instance's own `ptmx` inode, and this is what their loss looks like from the outside; the profile files are innocent. On 2026-09-27 the cause was `fix-dev.sh`'s old unchecked `umount` + `rm -rf "$RB_CHROOT/dev"`: the umount failed because rbp held the chroot's `/dev` open, and the `rm -rf` then deleted the **host's** device nodes *through the bind mount* (that code is gone — see [13](13-raspberrypi4.md)) | `ls -l /dev/ptmx /dev/null` — `ptmx` must be `crw-rw-rw- root tty` `5,2` and `/dev/null` a **character** device `1,3` (if a `>/dev/null` recreated it as a regular file, it is a disk-filling hazard: `rm -f /dev/null; mknod /dev/null c 1 3; chmod 666 /dev/null`). Then re-create the devpts inode by remounting it: `mount -t devpts devpts /dev/pts -o rw,nosuid,noexec,relatime,gid=5,mode=600,ptmxmode=000`, and `mknod /dev/ptmx c 5 2; chmod 666 /dev/ptmx; chown root:tty /dev/ptmx`. Confirm with a real login — `ssh -tt` should render `root@…:~#`. **The kernel-created nodes (`/dev/fb0`, `/dev/snd/seq`, `/dev/sda`, `/dev/dri/card0`, `/dev/input/event*`) come back only from a reboot**: `udevadm trigger` recreates udev's directories, never device nodes on devtmpfs. Until then rbp keeps running on fds opened before the wipe and **`systemctl restart rblive4` will fail into the `Restart=always` loop**. For a quick read on whether a pty exists at all, use `script -qec 'bash -li' /dev/null` (it says `failed to create pseudo-terminal`) or python's `pty.openpty()` (`out of pty devices`) — **`who` is only a tell inside a session that asked for a tty** (`ssh -t`): there it shows `pts/N`, while an `ssh host 'who'` without `-t` shows `sshd` and no pty column whether or not `/dev/ptmx` exists |
| **The UI takes a very long time to appear** | boot-time work that is not the player: cloud-init on the critical chain, the apt timers catching up a missed window, and (before the guard) ~9.8 s of systemd reloads from the launcher's no-op `systemctl` calls | `sh /opt/rblive4/boot-trim.sh report` — it prints the boot's monotonic milestones so a before/after is a diff. Its **`reloads` row reads 1**, which is NetworkManager's own; what must be **0** is the share attributable to the launcher, and the boot's own `Reload requested from client` lines name the caller. `boot-trim.sh status` says which items are applied; `install.sh` applies them, and `RB_BOOT_TRIM=0` turns that off ([13](13-raspberrypi4.md#boot-time)) |
| The player starts at boot and then **stops a few seconds later**, or the console appears over the UI | a display manager or `getty@tty1` started *after* `rblive4` and stopped it — `Conflicts=` is symmetric, and since the unit stopped waiting for `multi-user.target` it now starts **first** | `systemctl is-enabled lightdm gdm3 sddm getty@tty1`; anything but `not-found`/`disabled` is the cause. `sh /opt/rblive4/boot-trim.sh apply services` persists the disables (never a mask on `getty@tty1` — that breaks `systemctl start getty@tty1`) ([11](11-runtime-launcher.md#autostart)) |

## Display

| Symptom | Cause | Fix |
|---|---|---|
| No UI at all, but rbp is running | a framebuffer-memory shortfall, not a mode-set refusal — and on the measured Pi it is **fixed in the patch**, so a recurrence means the fix is not in the running tree (a stale `libdirectfb_fbdev.so`, or a chroot rebuilt before it). The fb has **one page** (`yres_virtual == yres`, `smem_len == 2560 × 800`); the stock driver forced `DLBM_TRIPLE` and its guard against a non-pannable fb tests `ypanstep == 0`, which this fb does not report, so `yres_virtual` tripled and the primary region test failed on `need_mem` 6,144,000 > `smem_len` 2,048,000. The patched driver decides the buffer mode from the **page count** instead, which is a `FRONTONLY` layer here. **If this appears after a different monitor was plugged in, it is not this defect** — a smaller fb fails the same `need_mem` check for a different reason; see [A monitor that is not 1280×800](#a-monitor-that-is-not-1280800) | read the `PRESENT:` line in `/tmp/dfbdig9.log`: `pages=1 pan=0` says the page decision was taken from the real geometry. `pages=3 pan=1` says the module is the old one — verify the sha256 in the chroot against `work/dfb/lib/directfb-1.4-6/systems/libdirectfb_fbdev.so` and re-deploy. For the arithmetic itself, add `debug=FBDev/Mode` to `usr/etc/directfbrc` and read `log/rbp.log` (the `=` and the slash are load-bearing: the parser splits options only at `=`, and the domain's declared name is `FBDev/Mode`, so `debug FBDev_Mode` is rejected as invalid and then ignored); `fbdump` says what the fb really is ([06](06-display.md), [13](13-raspberrypi4.md)) |
| rbp exits ~1 s after start, **`crash.log` shows `addr=0x30 r00=0x00000000`** (not the `[NULL+0x9c]` row above) | `DirectFBCreate()` failed, so it returned a NULL `IDirectFB*` — and rbp then dereferences it instead of stopping. `init_Resource()`'s error path prints a bare `DS_HW_Glib3_DFB.c <293>:` (the format string is literally `'%s <%d>:\n\t'`, with no body to lose) and then falls through into the success continuation, loading the NULL pointer and taking `vtable+0x30`. The **reason** `DirectFBCreate` failed is almost always that no module loaded at all | check the modules first, not the crash: `chroot /opt/rblive4/rbx3-run /usr/bin/arm-none-linux-gnueabi-dfbinfo` — `No system found!` means it. Then `cat /tmp/dfbdig4.log`: it names each directory searched and `opendir failed` on a miss. If the directory is `/lib/directfb-1.4-6/...` and does not exist, `module-dir` is missing from `usr/etc/directfbrc` — the build's `MODULEDIR` is `/lib/...` while the modules are staged at `/usr/lib/...` ([06](06-display.md#required-directfbrc)). Do **not** chase the NULL deref: it is a second, latent bug in rbp that a working DirectFB never reaches |
| `Unable to dlopen '…/._libdirectfb_fbdev.so'` and the same for the other modules | AppleDouble files from a macOS build host, left in the module directories. They are not inert: DirectFB walks each module dir and tries to dlopen every entry, so each one logs an error and the directory looks broken | `find /opt/rblive4 -xdev -name '._*' -type f -delete`. A re-deploy alone will **not** clear them — untar upgrades in place and never deletes — which is why `install.sh` and `build-chroot.sh` now both sweep them. If they are back after a fresh install, the tarball itself is carrying them: `tar -tzf work/rblive4-pi4.tgz \| grep '\._'` |
| `dmesg` shows `No compatible format found` | the mode was forced with a depth suffix | drop the `-16`/`-32` from the `video=` token; the 16 bpp default is the one we want ([13](13-raspberrypi4.md#the-hdmi-mode)) |
| Kernel text, a cursor, or boot messages over the UI | `fbcon=map:1` / `vt.global_cursor_default=0` not applied | `cat /proc/cmdline` — the tokens must be on the single existing line in `/boot/firmware/cmdline.txt` |
| Screen blanked mid-session | `consoleblank` unset | add `consoleblank=0`; a blank panel is a diagnostic red herring, not a crash |
| UI torn, or the render thread at 100% CPU | the `FBIOPAN_DISPLAY` pacer disabled or too small | `RB_PAN_PACER_MS` (default `16.666666`); `vc4` returns from a pan without waiting for vblank ([06](06-display.md)) |
| `EINVAL` from `fbset -depth`/`-xres` | **expected on Bookworm** — those are ignored | use `video=` on the kernel command line instead |
| UI sideways **(previous target)** | wrong `DFB_ROTATE` | that was the portrait panel; the Pi has no rotation. `RB_DFB_ROTATE=left` → `PRESENT_ROTATE, 90` still exists for it |
| Kernel oops/reboot as soon as rbp starts **(previous target)** | `directfbrc` missing → DirectFB took the GPU/dri path, and that unit booted `panic_on_oops=1` | keep `no-hardware` in `directfbrc`; the build is `--with-gfxdrivers=none --disable-dev-mem` and this is the verified configuration ([06](06-display.md)) |

### A monitor that is not 1280×800

The rows above are about the panel the unit was measured with. These are about
every other one — the case the `scale` rung exists for. **Read the `PRESENT:` line
first** in all of them: it carries the mode, the real geometry, and under `scale`
the rectangle that was actually drawn into.

| Symptom | Cause | Fix |
|---|---|---|
| Picture **sheared diagonally**, or **no UI at all**, after a different monitor is plugged in | under `off` the layer surface *is* the fb page, so a mismatch is not a slow picture but a broken one: a larger fb gets the logical 2560-byte stride inside a wider page (shear), a smaller one fails the primary region's `need_mem` check (no UI). **The driver now upgrades `off` to `scale` by itself**, so if this is happening something switched the upgrade off | `grep 'PRESENT: auto\|PRESENT: mode' /tmp/dfbdig9.log`. No `auto` line and `mode=off` with a mismatched `real_fb` ⇒ `RB_DFB_PRESENT_AUTO=0` is set somewhere (`rb.conf`, `rb.local.conf`, or the environment) — that is the control, not the default. `mode=scale` and still wrong ⇒ the next two rows |
| The UI is **cropped**, or sits off-centre with a bar on one side only | the rectangle is being taken from the fb rather than from the fit | compare the driver's `scale=WxH dx=N dy=N` with `fb_cursor.c`'s own `picture WxH at X,Y` in the shim log; they are independent reports of one rectangle, and `tools/fit-crosscheck.sh` is what keeps their two computations equal ([tools/README](../tools/README.md#fit-crosschecksh--the-two-copies-of-one-rule)) |
| Playback fine, **UI crawls** on a big panel | the software scaler is over its frame budget — the resample runs on rbp's `SCHED_FIFO 98` render thread | read the one-shot `PRESENT: N presented / M flips, avg X ms per present after 60 warmup, worst Y ms` line: that is the measurement, and `RB_DFB_PRESENT_PX_BUDGET` is the knob it sets. **Measured on this unit at the largest drill size (1728×1080): 3.34 ms average, 7.66 ms worst frame, no skip needed** — so the shipped budget is not the first thing to move; read the line before changing it. With `skip` already at 4 and still over budget, there is no frame rate to be had at that size: set a `video=` mode near 1280×800 and let the 1:1 path do it (`PRESENT: WARNING` in the same log names the remedy) |
| The picture is fine but the **arrow** stops short, or draws inside a bar | the cursor is mapping into the whole fb instead of the picture rectangle | `RB_POINT_CURSOR=0` confirms it is the arrow (the picture does not change); the two log lines above then say which side is wrong. On a matched 1280×800 panel this cannot happen — both rectangles are the identity — so a report of it is a report about a mismatched panel |
| Monitor swapped and the **picture is dead, rbp is fine** | the driver read the geometry once at open and holds it; so does the cursor | this is what the display watcher is for: `sh /opt/rblive4/display-watch.sh status`, then `$RB_LOG_DIR/displaywatch.log`. No baseline file (`/tmp/displaywatch.geom`) means the launcher never wrote one and the watcher will never fire — start rbp through `start-rb.sh`, not by hand |
| The watch log says `REFUSE: … — rbp is not running` | `systemd`'s `Restart=always` is already relaunching the player, and a restart fired here would race that bring-up | expected, and one of S10.6's outcomes. If it repeats forever, rbp is crash-looping: read `systemctl status rblive4` and the journal rather than the screen |
| `display-watch.sh: not found` on a deployed unit | it was added to the installer's explicit copy list, so an old deploy root predates it | re-run `install.sh`; the list is `for s in lib.sh fix-dev.sh start-rb.sh usb-watch.sh display-watch.sh rb.conf` |
| No `/dev/fb0` at all when nothing is plugged in | expected — vc4drmfb only creates the node for an attached connector. The unit deliberately has **no** `ConditionPathExists=/dev/fb0`, so the launcher runs and rbp exits; the watcher is not up, because it starts only after rbp is confirmed running | plug the monitor in and restart the unit. Whether rbp should instead wait for the framebuffer is **unmeasured** — S10.9 is the row, and it is not assumed either way |

## Pointing

| Symptom | Cause | Fix |
|---|---|---|
| The pointer does not move | either no pointer device was found, **or a `RB_POINT_KIND` pin in `rb.local.conf` excluded the one that is attached** | check the pin **first**: `abs` needs `EV_ABS`+`ABS_X`/`ABS_Y`+`BTN_TOUCH` and `rel` needs `EV_REL`+`REL_X`/`REL_Y`+`BTN_LEFT`, and a device that fails the filter is skipped **silently** — `/tmp/pointsrc.log` then has no `pointsrc:` line at all. This is measured: a `rel` pin left from a mouse hid a touch panel completely (2026-09-27, [13](13-raspberrypi4.md#s32-pointing)). If the pin is right, `tools/evdevdump --list`; set `POINT_KIND`/`POINT_DEV` from its verdict line ([07](07-touch.md)) |
| Fast clicks do nothing, slow ones work | rbp's UI debounce is longer than the click | raise `POINT_MIN_DWELL_MS` (default 45). This is the most likely report on this target |
| **The first tap after every start does nothing, and every tap after it works** | `tscfake_emit()`'s `last_down` was initialised to `-1` to mean "nothing emitted yet" — but `-1` is *truthy*, so `down && !last_down` was false for the process's **first** press and it went out as a single frame instead of the two-frame up→down burst. rbp's `TouchAdValueHysteresis` discards the first frame after a gap, so the first touch of every gesture was invisible — and the first touch of a process is always such a touch. Measured 2026-09-29: `work/menu17.sh` pressed rbp's INFO control seven times with the gate off, differing only in press length (150, 150, 45, 45, 30, 75, 150 ms) — **#1 did nothing and #2..#7 each flipped rbp's INFO view**, so the press length was never the variable | fixed in `tscfake.c` with a separate `primed` flag; `test_point.c`'s `test_first_emit()` pins it on the host (and must run **first** — a child forked after another test would inherit a primed tscfake and pass without testing anything). After the fix, `work/menu19.sh`'s ON phase shows the process's first touch **reacting** (549,764 px) |
| Clicks land mirrored or transposed | the axis algebra is wrong for this device | `POINT_SWAP_XY`/`POINT_INVERT_X`/`POINT_INVERT_Y`. **Do not derive it on paper** — measure with `POINT_DEBUG=1`, click the four corners, read `/tmp/pointsrc.log` |
| **Taps act on the mirror of where you touch** — the left sidebar's icons cannot be reached at all, while a full-width list still works, so it reads as "the touch works except on the left" | not a transform error at all: the panel is honest and **rbp acts at `1279 - x`** of the record it is given, so the shim has to write the reflection. If this ever appears again, the reflection was removed from `tscfake_emit()` | put it back ([07](07-touch.md#rbp-reflects-x-and-tscfake_emit-undoes-it)). Diagnose in one line from `POINT_DEBUG=1`: `logical=` vs `wire=` differ by `1279-x` **by design**; if they are equal, this is the defect |
| **A band along the very top of the screen is sluggish, or a swipe down from it unrolls a dark bar with six buttons** | **by design, and it is the price of the swipe-down menu**: the top 55 logical px **crossed with the middle third of the width** (`MZ_STRIP_Y1` × `MZ_ENTRY_X0..X1`, logical x 426..852) are swallowed by the shim so the gesture is reliable. It is `RB_POINT_MENU=1` doing it, not a calibration and not the transform. **Outside that zone nothing is swallowed at all** — the left and right thirds of the band are rbp's own controls on the frame they happen, which is where its `◄ INFO` button (x 1183..1258) lives, so INFO and BROWSE's sidebar cells are native again. Inside the zone, what rbp draws is **not dead** either: a tap that never becomes a swipe is replayed to rbp 45 ms later at the point the finger landed, which is how the middle of rbp's own top bar still answers. Only the *moment* is lost, and only for a tap; a swipe never reaches rbp at all | `RB_POINT_MENU=0` in `rb.conf`/`rb.local.conf` (then restart) stops the panel being drawn **and** makes the whole band rbp's with no delay — the honest baseline, and the fix if the 45 ms is perceptible. The delay is `POINT_MENU_TAP_MS` for the bench (not in `SHIM_VARS`). Making the zone smaller is a literal either way (`MZ_STRIP_Y1`, `MZ_ENTRY_X0/X1` in `menu_zone.h`) and needs a rebuild. **A control at the top-left or top-right that responds 45 ms late, or not at all, is the entry zone reaching further than it should**: re-measure the control's x against 426..852 before touching anything else ([07](07-touch.md#the-strip-costs-a-touch-its-timing-over-one-third-of-its-width)). Not a symptom at all: with the panel **open**, a swipe up or a tap off any button simply closes it and rbp sees nothing ([07](07-touch.md#the-swipe-down-top-menu-menu_zonec-menu_drawc)) |
| **Touching the UTILITY screen does nothing** — the whole screen is inert under a finger, while the same finger works on BROWSE, SOURCE and PERFORMANCE | **by design: rbp binds no touch on that screen.** It is the player's settings screen and it is driven by its own **selector** (`K_SELECTOR`), which is why the panel's MENU *hold* gets you there and then has nothing to hand you. Measured 2026-09-29, one session, so the null is bracketed by live controls: three taps in UTILITY — a setting's label, its value, and the category row — each changed **0 px** on a screen whose own 2 s drift is also 0, while one selector step moved it **126,396 px** and a tap on the SEARCH list seconds later moved **37,425 px** | use the FLX4's **browse rotary** to move and its **browse push** to enter (`map_flx4.c:589`, `:933`), or a keyboard's `↑`/`↓`/wheel and `Enter` (`map_kbd.c:170-173`). Nothing in the shim is involved and the top strip does not reach there. **Do not read a small diff on a browse screen as a reaction**: rbp marquees long track titles, so a no-touch 2 s drift control on that same screen reads **3,427 px** — bracket any tap against a drift control of the same length ([07](07-touch.md#utility-is-not-a-touch-screen)) |
| **The top menu flickers** — the band shimmers, and a finger sliding across it makes it worse | the panel is painted into the **same single page rbp draws into**, so rbp's own repaint erases the band 57 times a second and the witness thread puts it back. The repair copy is **82 µs** for the 143,360 B of the shipped 56-row band, and the rest of the miss is the **wait for the next poll** — which is the tick period and nothing else, so the period was re-priced at this height (`work/mm10.sh`) and the shipped default is **0.1 ms**, not the 0.5 ms inherited from the pointer arrow's own measurement. Separately, a press that changed which button is highlighted used to reclassify the whole 1280×112 panel under the lock, blanking the band for milliseconds | measured before and after the fix, 2026-09-29 (`work/menu13.sh` tags `before`/`after`, two slide directions each, a 169 µs sampler joined to a highlight sampler by `work/m13/align.py`): the longest run starting at a press boundary fell from **2090 and 4234 µs** to **1226 and 1922 µs**, and both of the before's over-2 ms runs are gone — while the miss fraction over the panel's *open* period is **unchanged at ~3.3 % in all four traces**. So the press blanking is fixed and what is left is the per-frame shimmer, which only a structural composite (F5) removes, at 1.4–2.4 ms of every 17.5 ms frame on rbp's own RT thread ([07](07-touch.md#the-flicker)). **Read the floor first, and read it at the height *and* the tick you are running:** at 0.5 ms the 56-row band measured **97.64–97.91 %** duty (a 12,000-sample window: 97.64 %, 275 miss runs, longest 1465 µs; a 30,000-sample one: 97.91 %, 617 runs, longest 1223 µs), against 97.05 %/1807 µs at 112 rows. At the shipped **0.1 ms** the same 12,000-sample window reads **99.11 %**, 107 runs, longest **908 µs**, total miss 0.94 % of the window — and **no sample at all** caught both of the band's border pairs missing, where 0.5 ms had 105. The price is +1.7 points of one core on the panel's own 4.13 % (`work/mm10.sh`, the sweep). So a ~2 % miss means a 0.5 ms tick is in force, not that anything is broken, and `POINT_MENU_MS` in the environment is the way to put it back without a rebuild. **A stale `/tmp/fbpanel` reports 0 % for a panel plainly on the screen**: it is looking for the old border colour `0xC67A` when the framebuffer holds `0xCE7A`, and a copy built for the 112-row band reads a 56-row panel with the wrong row count — rebuild with `gcc -O2 -static -o fbpanel work/fbpanel.c` **on the unit itself** |
| **Setting the menu off does nothing** — `systemctl set-environment RB_POINT_MENU=0` (or the same line in `rb.local.conf`) and the panel is still there after a restart | **the deployed launcher is older than the knob.** `start-rb.sh`'s `SHIM_VARS` loop is the only thing that turns `RB_POINT_*` into `POINT_*`, and it exports exactly the names it lists — so a launcher that predates a knob silently drops it, and the shim falls back to its in-source default. Measured 2026-09-29: the unit's `/opt/rblive4/start-rb.sh` had no `POINT_MENU` in `SHIM_VARS` and its `rb.conf` no `RB_POINT_MENU` line, so `RB_POINT_MENU=0` reached the service and stopped there | `grep POINT_MENU /opt/rblive4/start-rb.sh` says which launcher is deployed; deploy `rb.conf` and `start-rb.sh` with it (they ship as a pair — a stale `rb.conf` and a newer script disagree about names, which `rb_load_conf` refuses). To move **one** knob without a deploy, set the **shim name** instead: `systemctl set-environment POINT_MENU=0` — the launcher does not touch a name it does not list, and that is why `POINT_MENU_KEY_EXTRA` is settable that way ([08](08-controls.md)) |
| **A start-up line is missing from `/tmp/pointsrc.log`** — the menu gate line, `drawing the panel`, or `cursor: …` — while other lines from the same start are there | **not a phase that never ran: the logger dropped it.** `pointsrc_log()`'s one-shot open published `log_tried = 1` before `log_fp = fopen(…)` under no lock, and returned silently on NULL — so any call in flight while another thread was inside its `fopen()` was lost, and silently, because NULL also means "the log could not be opened". Every one of these lines is written **once per process**, so a dropped one is dropped for the life of that process. Measured 2026-09-29 (`work/menu20.sh`, six starts before and twelve after): **6 of 6 starts lost at least one of the four one-shot lines** on the unfixed shim and **0 of 12** after the fix — in a reciprocal shape, which is the mechanism's signature. 5 of the 6 lost the reader's *pair* (`absolute device` + `raw range`, adjacent in the code) while the caller's gate line survived, and 1 lost the gate line while the reader's pair survived; with `POINT_MENU` unset, 2 of 6 lost `cursor: …` instead, and `work/menu19.sh` lost a phase's signature in **both** of its phases | fixed with `pthread_once()` in `pointsrc.c`. On a shim older than that, read **which** lines survived before concluding anything: a whole pair lost together, or one framebuffer-opener's line, is the fingerprint, and a one-shot line is evidence only when it is there |

The mirror absorbs it — a 512-frame prefill of silence at each stream start, plus a **repeat of the last delivered frame** (a zero-order hold) when the level falls | `padframes` advancing at ~7/s is normal, not a fault, and so is the granularity: the pads arrive **32–41 frames at a time, one every 5.2–6.5 s**, because `snd_pcm_avail_update()` on a hw PCM reports against a `hw_ptr` that steps a whole period at a time. That granularity is why the content is a hold and **was silence until 2026-09-30** — 0.8 ms of silence is an envelope notch, i.e. the tick, where holding a frame is one step ([09](09-audio.md#two-clocks-no-resampler)). `padsilent` must stay **0** after the first block: it counts pads with no delivered frame to hold, so a non-zero reading means the silence is back. A *gap* is the XRUN path, so check `retries`: it should stay where the stream start left it. If the correction is not running at all, look for `pads` never moving — that is what an unresolved `snd_pcm_avail_update` looks like. Drift beyond a few hundred ppm is the one shape this design does not fix; it would need a resampler ([09](09-audio.md#two-clocks-no-resampler)) |
